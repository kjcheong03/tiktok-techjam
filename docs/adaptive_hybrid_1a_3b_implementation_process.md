# Adaptive Hybrid 1A-3B Implementation Process

## Goal and boundary

The final GhostLab agent must implement the six architectural requirements in the
TikTok TechJam Track 4 problem statement:

1. **1A - Dual-Track Routing**
2. **1B - Multi-Route Retrieval to LLM Semantic Ranking**
3. **2A - Dynamic State Machine**
4. **2B - Proactive Guidance**
5. **3A - Runtime Adaptation**
6. **3B - Adaptive Orchestration**

These requirements define the fixed architecture. GhostLab may optimize the
implementation inside each section, but a final candidate may not disable, bypass
or make any section decorative.

Research configurations may switch components off for ablations. Submission
eligibility requires all six sections to be active and behaviourally demonstrated.

The newly fitted fixed Adaptive Hybrid architecture is promotion control C. The
complete deterministic Buying path is the runtime fallback. Historical guarded
champion results remain reference evidence; they are not the required architecture or
the current promotion control.

## Architecture enforcement

A final candidate is eligible only when:

1. all six sections are implemented;
2. every section changes observable behaviour when relevant;
3. runtime features contain only observable information;
4. every response satisfies the official contract; and
5. the complete path is evaluated before GhostLab optimizes its internal choices.

GhostLab then maximizes effectiveness and efficiency among eligible candidates.

## GhostLab campaign integration

The adaptive runtime is integrated with the existing GhostLab research engine
without making the six architectural sections optional. The integration uses two
separate contracts:

1. `AdaptiveArchitectureAudit` validates the required component identities,
   ordering, three-source evidence, literal local-LLM capability, profile influence,
   fallback and atomic commit for every materialized candidate.
2. `AdaptiveTechniqueRegistry` exhaustively classifies every catalog record as a
   compulsory implementation, promotable adaptive addition/slot implementation,
   non-promotable control, research procedure or unavailable technique.

The current catalog contains 88 records. The exact counts are generated by the
registry and are not architectural constants. Plan-only validation currently
classifies 19 compulsory implementations, 20 promotable implementations/additions,
22 controls, 16 research procedures and 11 unavailable records. Adding a technique
to the catalog makes the registry fail closed until that record is classified; no
technique can silently disappear.

| GhostLab behavior | Adaptive 1A-3B rule |
|---|---|
| Compulsory capability | Always present; implementation parameters and fitted assets may be optimized |
| Promotable implementation/addition | Tested alone, in compatible pairs and in higher-order beam combinations |
| Control-only technique | May produce evidence but cannot replace or bypass a required capability |
| Fit-required challenger | May race, but cannot become champion without verified fold-safe fit evidence |
| Research procedure | Drives search/evaluation and is never mistaken for a runtime component |
| Unavailable technique | Retained with its blocking reason and retest trigger |

`AdaptiveGhostLabEngine` preserves a matched incumbent, runs F0/F1/F2 racing,
prunes dominated structures, retains an exploration beam, expands survivors into
higher-order combinations, and performs conditional local BOHB tuning around each
surviving structure. Candidate and wall budgets bound work; there is no six-
technique champion limit. The maximum combination size defaults to the number of
currently promotable techniques and can be lowered only as an explicit resource
budget.

The following additions now execute at declared hooks without changing the
architecture: weighted/RRF/sparse-first three-route merge implementations, catalog
quality prior, guarded catalog PRF, early facet diversity, and historical
lexical/GBDT/LambdaMART/rank-ensemble ranking signals. The historical rankers are
bounded auxiliaries after the compulsory source-aware union GBDT: they cannot replace
the primary model, change candidate membership, bypass constraint authority or affect
more than their configured head. PRF obeys the 2B overload cutoff; quality and
diversity run after complete-pool union ranking and before the semantic slot.

## Static workflow contract

The workflow topology is immutable after this plan is accepted. Training may
change the implementation selected for a slot, but it may not change the order or
remove a required slot.

The runtime configuration will use a dedicated schema similar to:

```python
AdaptiveHybridConfig(
    architecture="adaptive_hybrid_1a_3b_v1",
    state=RequiredStateV2Config(...),
    router=RequiredDualTrackRouterConfig(...),
    buying=RequiredPrecisionTrackConfig(...),
    browsing=RequiredDiverseDenseTrackConfig(...),
    merger=RequiredMultiRouteMergeConfig(...),
    semantic_ranker=RequiredLocalLLMRankerConfig(...),
    guidance=RequiredOverGeneralityGuidanceConfig(...),
    runtime_adaptation=RequiredProfileContextConfig(...),
    orchestration=RequiredCoordinatorConfig(...),
    residual=OptionalResidualConfig(...),
)
```

Required fields have no `off` value in a submission configuration. Research-only
ablation configurations may disable a field, but they are marked
`submission_eligible=false` before evaluation and cannot be promoted.

The configuration validator must reject a final candidate when:

- a required component or local asset is missing;
- Buying does not resolve to Field BM25 precision retrieval;
- Browsing does not resolve to diverse dense retrieval;
- the 1B merge cannot consume keyword, category and vector evidence;
- category evidence cannot add candidates;
- the union ranker cannot score the complete merged pool;
- the local-LLM semantic stage is disabled or unbounded;
- overload guidance cannot produce a legal question action;
- runtime adaptation omits confidence, provenance or conflict handling;
- orchestration does not validate and atomically commit the selected action; or
- the configured workflow order differs from the canonical diagram.

## Runtime component interfaces

The new coordinator will compose existing GhostLab components through typed,
side-effect-free interfaces:

| Interface | Responsibility | Fixed or optimizable |
|---|---|---|
| `StateV2Reducer` | Observe user messages, accumulate state and handle overrides | Behaviour fixed; parsing confidence optimizable |
| `RuntimeContextAdapter` | Combine State V2 with conflict-safe profile context | Required; confidence and influence optimizable |
| `DualTrackRouter` | Select Buying or Browsing with confidence and reason | Required; model and threshold optimizable |
| `PrecisionTrack` | Produce Field BM25 precision candidates and safe fallback | Required; weights/depth optimizable |
| `DiverseDenseTrack` | Produce E5 semantic Browsing candidates | Required; views/depth optimizable |
| `MultiRouteMerger` | Combine keyword/category/vector evidence with provenance | Required; budgets/scoring optimizable |
| `UnionRanker` | Score every executable merged candidate | Required; model/features optimizable |
| `LocalLLMSemanticRanker` | Bounded semantic reorder of the preliminary head | Required; SmolLM2/Browsing policy fixed, bounded weight/depth schedule optimizable |
| `OverGeneralityGuidance` | Decide cutoff and highest-value unresolved question | Required; signals/value model optimizable |

## How the existing GhostLab engine adapts

GhostLab remains the main research, training, optimization and evidence engine.
The existing guarded runtime and `ExperimentalAgent` remain unchanged as controls.
The adaptive implementation adds a new composition path rather than forcing the
flat experimental runtime to simulate a workflow it does not represent.

The integration will add:

1. an `AdaptiveHybridConfig` loader and validator;
2. a `build_adaptive_hybrid_agent(...)` factory;
3. the fixed `AdaptiveHybridAgent` coordinator;
4. adapters around existing State V2, BM25, E5, ranking, question and normalization
   components;
5. GhostLab bindings that vary only optimizable fields in the fixed schema; and
6. activation support in `SelectedRuntime` only after the final preset is frozen.

GhostLab may return one of three decisions for a required slot:

- **accept implementation** - retain the evaluated implementation;
- **replace implementation** - test another implementation of the same required
  capability; or
- **constrain implementation** - reduce its budget, weight or activation scope and
  use observable abstention.

It may not return **remove capability** for any part of 1A-3B. Optional components
may still be rejected completely.

## 1A - Dual-Track Routing

### What will be implemented

Implement an intent controller that returns:

```python
RouteDecision(
    action="buying" | "browsing",
    confidence=float,
    reason=str,
)
```

- **Buying** explicitly selects Field BM25 high-precision retrieval and locks
  supported, high-confidence hard constraints.
- **Browsing** explicitly selects diverse E5 dense retrieval for semantic,
  scenario and cross-category candidate discovery.
- Low confidence, invalid output or router failure abstains to the complete Buying
  precision path.

This section defines the primary route. Keyword, category and vector evidence are
combined later inside 1B; they must not be used to blur the distinction between
Buying precision retrieval and Browsing diverse dense retrieval.

The controller may use constraint count/confidence, category and query specificity,
negative constraints, sparse margin/entropy, correction state, profile conflict and
turn. It may not use the official scenario label.

### Existing work to reuse

- State V2 observable state and views;
- validated field-weighted sparse retrieval;
- the complete deterministic State V2 Buying precision path; and
- existing leakage-safe routing infrastructure.

### What GhostLab may optimize

Observable feature subset, model, calibration and abstention threshold.

### Required proof

- A precise request selects Buying.
- An open-ended request selects Browsing.
- Both routes are reachable without scenario labels.
- Low confidence and failure select the complete precision path.

## 1B - Multi-Route Retrieval to LLM Semantic Ranking

### What will be implemented

After 1A selects the primary track, the shared 1B stage combines keyword, category
and vector similarity in one bounded in-memory candidate merge. Category retrieval
is implemented inside this stage; it is not an additional top-level route.

**Keyword route:** reuse field-weighted BM25. It is the explicit primary generator
for Buying and may provide only bounded supporting evidence to the later 1B merge
when Browsing is primary.

**Category evidence inside 1B:** use a catalogue category index that can add products
to the merge rather than merely score products already found by BM25 or E5. Buying
uses exact or ancestor-compatible categories. Browsing may include
context-supported related or sibling categories for cross-category discovery.

**Vector route:** use the local, revision-pinned E5 product index and deterministic
State V2 query views. It is the explicit primary generator for Browsing and may
provide only bounded supporting evidence to the later 1B merge when Buying is
primary. Start from the validated multi-view relevance-only approach; MMR is not
required.

Merge candidates into a bounded, deduplicated pool while preserving:

```python
Candidate(
    parent_asin=str,
    routes=frozenset({"keyword", "category", "vector"}),
    sparse_score=float | None,
    sparse_rank=int | None,
    category_score=float | None,
    category_rank=int | None,
    dense_score=float | None,
    dense_rank=int | None,
)
```

A union-aware ranker must score the complete pool. Appending category or dense
candidates below a ranker that never examines them is invalid.

The route decision determines primary evidence and budgets, but both branches feed
the shared 1B merge shown in the organiser-aligned architecture. High-confidence
Buying constraints remain locked through union and semantic ranking.

After union ranking, every successful non-fallback turn reaches a mandatory
semantic-ranking slot over the final Top-10 head. Its observable activation policy
may invoke the bounded local LLM or select a deterministic pass-through when
semantic inference is not useful. The slot and LLM capability cannot be disabled;
both actual activations and justified skips must be demonstrated. The selected
model type, revision, licence and hashes must be documented.
The LLM receives the distilled request and concise catalogue fields, uses
deterministic decoding and may only reorder supplied catalogue IDs.

An existing cross-encoder can be evaluated as a semantic fallback, but it must be
described accurately rather than declared equivalent to a literal LLM. Timeout,
malformed output, invalid scores or unknown IDs select the complete precision
ranking.

### What GhostLab may optimize

Candidate depths, category expansion, E5 views, union budget, union ranker and features.
For the compulsory semantic slot, the model, prompt and activation policy are fixed;
GhostLab may tune only the declared weight/depth schedule.

### Required proof

- Keyword, category and vector evidence each add candidates within 1B.
- Provenance, route scores and original ranks survive merging.
- Category-only and vector-only products enter union-aware ranking.
- The local LLM changes at least one validated ordering.
- Final recommendations are unique, catalogue-valid and capped at ten.
- Dense or semantic failure returns the complete precision path.

## 2A - Dynamic State Machine

### What will be implemented

Make State V2 the production source of truth for:

- raw history and active intent;
- incremental and compatible preferences;
- exclusions, declines and no-preference attributes;
- constraint confidence, provenance and source turn;
- targeted correction;
- category/global Intent Override and slot rewriting;
- intent epochs; and
- intent-scoped shown-product history.

At the start of each turn, commit the observed user message and create one immutable
snapshot used by all route, retrieval, ranking and question proposals.

On Intent Override, increment the epoch where appropriate, supersede incompatible
constraints, retain only compatible preferences, reset intent-scoped shown-product
history and rebuild all queries.

Candidate policies are non-committing. After response validation, atomically commit
only the route, question and recommendations actually returned. Rejected proposals
must not change `asked_attributes`, `shown_products` or action history.

### What GhostLab may optimize

Parsing confidence and override-scope decisions without weakening accumulation,
correction or override semantics.

### Required proof

- Preferences accumulate across turns.
- Targeted correction replaces only its slot.
- Intent Override removes stale incompatible state and changes retrieval.
- Rejected proposals create no action-history side effects.
- Committed action history exactly matches the returned response.

## 2B - Proactive Guidance

### What will be implemented

Use a cheap bounded preview of the selected track and 1B candidate evidence before
further candidate expansion. Detect candidate overload from observable
specificity, unresolved constraints, retrieval margin/entropy, candidate count and
category/facet spread.

When overload is detected:

1. stop further candidate expansion for that turn;
2. merge the keyword, category and vector evidence already collected;
3. complete union ranking and apply the mandatory semantic activation decision;
4. enumerate unresolved legal attributes;
5. remove answered, declined and no-preference attributes;
6. estimate each remaining question's continuation value including MTTC cost; and
7. select the highest-value question only when its value is positive.

The action remains recommend-and-ask. Ask-only deferral stays separately disabled
unless independently tested and promoted.

### What GhostLab may optimize

Overload signals, thresholds, question-value estimator and stopping threshold.

### Required proof

- Specific requests do not trigger overload guidance.
- Over-general requests stop expensive expansion.
- The selected question is legal, unresolved and highest-valued.
- Answered, declined and no-preference attributes are not repeated.
- Recommendations remain present when a question is asked.

## 3A - Runtime Adaptation

### What will be implemented

Distil accumulated dialogue, State V2 and the supplied user profile into an
immutable context used by routing, retrieval, ranking and clarification.

Create a separate conflict-safe profile output:

```python
ProfileUpdate(
    values=tuple(...),
    confidence=float,
    provenance=tuple(...),
    conflicts=tuple(...),
)
```

The supplied profile is the available long-term context. A session-scoped overlay
is updated from observed dialogue without introducing cross-session evaluator
memory. Precedence is fixed:

```text
explicit current-epoch session intent
> current conversation evidence
> supplied aggregate profile
```

Conflicting profile evidence is suppressed. Every retained value carries
confidence and provenance. At the start of a turn, the latest stored context
produces the current route, retrieval, ranking and question inputs. After the
selected response is committed, 3A updates the session-scoped profile overlay and
context for the next turn, matching the feedback loop in the canonical diagram.

### What GhostLab may optimize

Profile confidence, conflict gating and the influence of compatible profile
evidence. Explicit session intent may never lose precedence.

### Required proof

- Compatible profile evidence affects an ambiguous request.
- Explicit session intent defeats conflicting profile evidence.
- Profile-derived values expose confidence and provenance.
- No profile or state leaks between sessions.

## 3B - Adaptive Orchestration

### What will be implemented

Implement one coordinator that owns the complete turn:

```python
state.observe(message, turn)
snapshot = state.immutable_snapshot()

context = runtime_adapter.current_context(snapshot, supplied_profile)

# Always create the safe complete Buying precision fallback.
precision = precision_route.retrieve_and_rank(context)

try:
    route = intent_router.decide(context, precision.signals)
    primary = (
        precision.candidates
        if route.action == "buying"
        else diverse_dense_route.retrieve(context)
    )
    preview = multiroute_merger.preview(context, route.action, primary)
    overload = overload_detector.decide(context, preview)

    merged = multiroute_merger.collect(
        context=context,
        primary_route=route.action,
        primary_candidates=primary,
        stop_after_preview=overload.triggered,
    )
    ranking = union_ranker.rank(context, merged, route.action)
    ranking = local_llm_ranker.rerank_if_needed(
        context, ranking, route.action, overload.triggered
    )
    question = question_policy.highest_value(context, ranking)
    reason = (
        "overload_cutoff" if overload.triggered
        else f"{route.action}_multiroute"
    )

except (TimeoutError, InvalidScoreError, LowConfidenceError) as error:
    ranking = precision.ranking
    question = question_policy.safe_fallback(context)
    reason = fallback_reason(error)

response = response_validator.normalize(
    ranking,
    question,
    valid_catalog_ids=catalog_ids,
    top_k=min(top_k, 10),
    deduplicate=True,
)

state.atomic_commit(
    route=route_or_fallback,
    asked_attribute=response.ask_attribute,
    shown_products=response.recommendations,
)
profile_update = runtime_adapter.update_after_selected_turn(
    snapshot=snapshot,
    selected_response=response,
)
trace.record_observable_decision(...)
return response
```

Dense, category, LLM or routing timeout, corrupt assets, invalid scores,
insufficient candidates and low confidence all select the complete precision path.

The trace records route/confidence, overload, question value, candidate provenance,
component contribution, fallback reason and component latency. It contains no
target, scenario, future-answer, evaluator or hidden-reward information.

### What GhostLab may optimize

Activation thresholds and bounded runtime budgets while preserving the complete
turn order and fallback semantics.

### Required proof

- Later-turn context changes a route, query, ranking or question decision.
- Adaptive failure returns a valid precision response.
- Every response contains at most ten unique catalogue IDs.
- Every selected workflow action has a reason code.
- State action history exactly matches the normalized response.

## Runtime leakage prohibition

Router, ranker, profile, overload, LLM and question-policy runtime features must
exclude:

- official scenario labels;
- target IDs or target membership;
- evaluator outcomes and metrics;
- future messages or answers;
- hidden simulator state or reward; and
- validation-fold identity.

These values may be used only as offline labels or evaluation outcomes.

## GhostLab training and optimization lifecycle

### 1. Establish one compliant baseline

Before automated optimization, implement the simplest deterministic version of
every required slot. This baseline establishes that the complete workflow runs and
that every component receives and produces the intended data.

It is not selected for final score at this stage. A required component may perform
poorly, but it must be real, bounded and observable so GhostLab can measure and
improve it.

### 2. Generate leakage-safe training data

Use grouped session folds. Every turn from a session stays in the same outer fold.
For each training fold, replay the exact canonical workflow and generate the same
state snapshots and candidate pools the runtime will consume.

- The union ranker trains on exact keyword/category/vector merged candidates.
- Router labels come from replaying Buying and Browsing actions at the same state.
- Question labels compare legal recommend-and-ask continuations including MTTC
  cost.
- Profile-gating examples compare compatible and conflicting current intent.
- LLM prompt/model selection uses only training-fold or explicitly designated
  selection data.
- No fitted asset may include its outer validation sessions.

Each learned asset records its training IDs, feature schema, configuration, seed,
catalogue hash and asset hash in a fit receipt.

### 3. Measure headroom before fitting

GhostLab first determines whether a trainable choice exists:

- compare Buying and Browsing actions at identical states;
- measure whether category/vector candidates add reachable targets;
- measure whether a complete-pool ranker can promote added candidates;
- enumerate legal questions and their continuation values;
- compare profile-compatible and profile-suppressed contexts; and
- measure whether local-LLM scoring can improve preliminary ordering.

Headroom analysis guides implementation replacement and budget allocation. It does
not authorize removing a required capability.

### 4. Optimize one slot at a time

Freeze the rest of the compliant runtime while optimizing one uncertain slot. This
prevents GhostLab from attributing a gain to the wrong component.

Recommended order:

1. exact multi-route candidate production;
2. union-aware ranking;
3. bounded local-LLM semantic ranking;
4. Buying/Browsing routing and abstention;
5. overload detection and question value;
6. conflict-safe profile influence; and
7. bounded joint parameter search.

Each selected implementation receives a backward ablation. Ablations may disable
required slots for measurement, but their configurations remain ineligible for
submission.

### 5. Run bounded joint optimization

After individual slots work, GhostLab may search compatible combinations of route
thresholds, candidate budgets, ranking weights, the bounded semantic schedule, question thresholds
and profile confidence. The search space is generated from the required adaptive
schema, so no trial can silently collapse the architecture.

Candidates are ranked lexicographically:

1. architecture/schema validity;
2. behavioural capability validity;
3. leakage and asset validity;
4. runtime feasibility;
5. official TechnicalScore and scenario safety; and
6. simplicity when evidence is otherwise tied.

## Resolving empirical uncertainty

| Uncertainty | First evaluation | Response if unsuccessful |
|---|---|---|
| Literal local LLM | Compare a small local shortlist on deterministic bounded semantic ranking; measure valid-output rate, ordering changes, quality, latency and memory | Replace with a smaller or quantized local LLM, reduce depth/product text or revise the prompt; keep an accurately named cross-encoder only as fallback |
| Union-aware ranker | Train on exact fold-local merged candidates and compare sparse-only candidates with the same ranker against the complete merge | Replace features/model, reduce the union budget or strengthen Buying constraint protection; do not return to a ranker that cannot inspect merged candidates |
| Buying/Browsing router | Measure counterfactual route headroom at identical observable states, then fit/calibrate a shallow action-value model | Use conservative specificity rules and abstention while retaining genuine reachability of both tracks |
| Diverse dense retrieval | Measure unique vector candidates, category spread and target reach before and after the 1B merge | Replace E5 views/depth or candidate selection while retaining the diverse dense Browsing track |
| Category evidence | Measure products uniquely added by category lookup and their downstream ranks | Replace category inference/expansion or cap its budget; keep category evidence inside 1B |
| Question value | Replay every legal unresolved question with full continuation reward and MTTC cost | Replace the learned estimator with deterministic information gain plus a positive-value threshold and fixed fallback order |
| Profile adaptation | Compare identical ambiguous requests with compatible profile, suppressed profile and explicit conflict | Reduce influence and restrict activation to ambiguous states while retaining confidence/provenance and explicit-intent dominance |

No single failed experiment rejects the architecture. Repeated failures narrow the
implementation until the required capability is safe, bounded and genuine.

## Full-engine validation plan

Validation applies to the complete engine, not only isolated models.

### Level 1 - Schema and static architecture

- Reject missing or disabled required slots.
- Verify the configured order matches the canonical diagram.
- Verify all assets are local, declared and hash-pinned.
- Verify model licences and offline availability.
- Verify no protected data paths or forbidden runtime features are referenced.

### Level 2 - Unit contracts for 1A-3B

- **1A:** both routes are reachable, confidence is bounded and abstention is safe.
- **1B:** all three evidence types enter the merge, provenance survives, the full
  pool is scored, local-LLM output is candidate-bounded, and semantic activation
  has both a validated active case and a justified deterministic skip.
- **2A:** accumulation, correction, override, epoch change and atomic action history
  are correct.
- **2B:** overload cutoff and highest-value unresolved question are deterministic.
- **3A:** profile confidence/provenance and explicit-intent precedence hold.
- **3B:** the coordinator executes the canonical order and every failure returns a
  normalized precision response.

### Level 3 - Component interactions

- State changes rebuild all route queries and features.
- Buying constraints remain locked after merge and semantic ranking.
- Browsing dense candidates can enter the union ranker and final Top 10.
- Category evidence can add candidates inside 1B.
- Overload prevents further candidate expansion but still executes the mandatory
  union and LLM ranking stages on the bounded collected pool.
- The question actually returned is the only question committed.
- Recommendations actually returned are the only products marked shown.
- Profile conflicts cannot influence retrieval or ranking.

### Level 4 - Behavioural architecture validation

Run deterministic diagnostic cases proving:

1. a precise request selects Buying and Field BM25;
2. an open-ended request selects Browsing and diverse dense retrieval;
3. keyword, category and vector evidence are present in 1B;
4. local-LLM semantic ranking changes a valid ordering;
5. Intent Override rewrites state and changes the next result;
6. an overloaded request cuts off expansion and asks the highest-value question;
7. compatible profile context affects an ambiguous request;
8. explicit current intent defeats a profile conflict; and
9. later-turn context changes route, ranking or guidance behaviour.

A final candidate fails architecture validation if a required component is always
inactive, always falls back or never changes observable behaviour.

### Level 5 - Leakage and fold audit

- Keep complete sessions in one fold.
- Verify fit receipts exclude outer validation IDs.
- Scan runtime features for scenario, target, evaluator, future-answer, reward and
  fold identifiers.
- Verify selection uses development data only.
- Keep synthetic and independent-template results labelled diagnostic.
- Confirm F3 remains sealed.

### Level 6 - Grouped end-to-end evaluation

Compare A stateless BM25, B tagged-best Dynamic Conversation State, C fixed Adaptive
Hybrid and each development finalist D on identical ordered development sessions under
the shared evaluator contract. Only C and a single development-selected D participate
in promotion.

Report:

- HitRate@10, MRR, MTTC, Efficiency and TechnicalScore;
- all scenario and outer-fold results;
- paired wins, ties and losses;
- paired confidence interval and randomization p-value;
- Buying/Browsing route counts, confidence and abstention;
- unique keyword/category/vector contribution and final Top-10 contribution;
- local-LLM activations, ordering changes and invalid-output count;
- overload cutoffs, question actions and estimated values;
- profile activations and conflicts; and
- fallback reasons and counts.

Thresholds for score, scenario safety and latency are frozen before the final
selection run. A failed threshold causes implementation replacement or constraint,
not removal of a required capability.

### Level 7 - Operational engine validation

- Run deterministic replay twice and compare response and trace hashes.
- Run with network access disabled.
- Measure model/index cold load, warm p50/p95 latency, peak memory and asset size.
- Inject router, dense, category and local-LLM timeout/invalid-output failures.
- Verify each adaptive failure returns the complete valid precision response.
- Validate at most ten unique catalogue IDs on every turn.
- Run the existing regression suite for all reused components.
- Run lint, formatting and type checks on the new runtime.

Multi-user concurrency stress, UI validation and external-service testing remain
out of scope because they are not required by the official isolated-session
contract.

### Level 8 - Compile, factory and official-entrypoint validation

- Build the agent from the frozen adaptive preset through its production factory.
- Verify the research-built and factory-built agents produce identical responses.
- Package all required local assets and verify their hashes.
- Verify `starter.Agent` parity with the frozen adaptive agent before activation.
- Verify the complete deterministic Buying path remains available as the runtime
  precision fallback.
- Update `SUBMISSION_MANIFEST.json` only after the selected runtime is frozen.
- Do not create or change `configs/active_candidate.json` until a reviewed human
  activation decision.

### Validation outcome

The engine receives one of these outcomes:

- **architecture incomplete** - a required 1A-3B capability is missing or
  decorative; implementation continues;
- **architecture complete, optimization required** - the full workflow operates but
  score, safety or runtime needs improvement;
- **development validated** - architecture, behaviour, OOF evidence and operations
  pass; candidate may be frozen for reviewed activation; or
- **submission frozen** - the reviewed candidate, configuration and assets are
  immutable and ready for the separately governed final evaluation.

## Complete process

### 1. Create an isolated branch and worktree

Branch from the reviewed canonical commit. Preserve the source worktree and guarded
champion. Do not access F3 or activate `configs/active_candidate.json`.

### 2. Implement the complete 1A-3B runtime

Reuse accepted State V2, sparse, E5, ranking, evaluation and normalization code.
Implement every missing capability above and expose one typed adaptive
configuration in which all six requirements are mandatory. Produce one runnable
agent through the official `reset(...)` and `respond(...)` interface.

### 3. Run focused tests

- **1A:** both routes, observable inputs and abstention;
- **1B:** three-source candidate contribution, union ranking, bounded local LLM
  and valid IDs;
- **2A:** accumulation, correction, override and atomic commit;
- **2B:** overload cutoff, highest-value question and recommend-and-ask;
- **3A:** profile provenance, confidence and explicit-intent dominance; and
- **3B:** complete ordering, fallback, trace and normalization.

Run regressions for reused components. Do not add unrelated concurrency, UI or
external-service work.

### 4. Establish the compliant end-to-end baseline

Use only lineage-safe development sessions. Compare:

1. A: official stateless BM25 reference;
2. C: complete fixed Adaptive Hybrid 1A-3B control; and
3. D1-D3: the available one to three development-selected GhostLab finalists.

A is explanatory. Freeze every development-eligible D configuration using development evidence, capped at three.
On the one-time 550-session final selection set, gate each D against C and choose among
passing D systems using only the predeclared tie-breaks; otherwise retain C.

Report HitRate@10, MRR, MTTC, Efficiency and TechnicalScore, plus direct 1A-3B
behaviour: route counts, candidate-route contribution, local-LLM ordering changes,
overload/questions, profile conflicts, fallback counts and component latency.

Use backward ablations only to verify component contribution. An ablation that
removes a required capability cannot become the final submission candidate.

This run answers whether the fixed workflow is complete and where its measurable
headroom lies. It is the starting point for GhostLab optimization, not the final
selection run.

### 5. Let GhostLab optimize the implementation inside every required slot

GhostLab consumes the baseline traces, exact fold-local candidate pools and fit
receipts. It may optimize the router, Buying retriever, Browsing retriever,
candidate merge, union ranker, local-LLM configuration, overload policy, question
policy, profile influence, fallback thresholds and resource budgets.

Run isolated slot experiments first, followed by bounded joint search. Every trial
is constructed through `AdaptiveHybridConfig` and rejected before scoring if it
changes the canonical order, disables a required slot, makes a required capability
decorative, violates the leakage rules or cannot execute offline.

For a required slot, an unsuccessful experiment means GhostLab must retain the
last compliant implementation, replace its algorithm or constrain its influence.
It does not remove the slot. Only explicitly optional downstream components may be
rejected completely.

### 6. Validate the selected complete engine

Freeze the best architecture-compliant development candidate and execute all eight
validation levels in this document. This includes schema validation, focused unit
and interaction tests, behavioural proof cases, fold/leakage audit, grouped
end-to-end comparison, deterministic offline replay, failure injection, resource
measurement, factory parity and official-entrypoint parity.

Compare the frozen candidate with both controls using the predeclared score,
scenario-safety and runtime thresholds. Diagnose any failure at its owning slot,
then return that slot to Step 5 without changing the static workflow.

### 7. Analyse, freeze and hand off

Identify score and scenario changes, behavioural contribution, route/question
errors, candidate/ranking bottlenecks, latency and the bounded variables GhostLab
optimized. Record the selected configuration, model/index hashes, fit receipts,
fold definitions, metrics, reason-code counts and fallback counts.

The implementation becomes the architectural base when all six sections work end
to end. It becomes eligible for reviewed activation only after the selected
complete engine is effective, feasible and reproducible. F3 access, manifest
replacement and production activation remain separate governed decisions.

## Optional and out of scope for this pass

MMR, category quotas, membership-preserving residual reranking, generative
customer-facing explanations, persistent cross-session learning, external vector
databases, paid APIs, UI work, multi-user concurrency hardening, F3 evaluation and
production activation are not required to complete 1A-3B.

## Completion condition

One official-interface agent must execute the full 1A-3B turn sequence, pass its
focused tests, complete grouped public end-to-end evaluation, emit observable
reason codes and leave GhostLab with bounded optimization choices without allowing
it to remove a required architectural capability.
